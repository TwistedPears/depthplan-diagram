# Projects v1 — UX and document lifecycle

Status: implementation-ready design for [#11](https://github.com/TwistedPears/depthplan-diagram/issues/11), prepared for a documentation PR. This describes proposed Projects behavior; the current application does not implement it yet. User decisions and delegated v1 defaults are recorded in [decision-checklist.md](decision-checklist.md). The [wireframes](wireframes.html) extend the four accepted [image concepts](../../design/project-ui-concepts-2026-09-26/README.md). [validation.md](validation.md) records the design walkthrough and acceptance mapping.

## 1. Product boundaries

DepthPlan starts with its existing blank canvas. A person can create, open, edit, save, and export a standalone board indefinitely. Projects are an optional way to organize independent boards in a local folder.

Reuse the current window. Opening a project adds the Project widget and open-board tabs to the existing canvas UI. Closing it returns to the standalone blank canvas. Keep drawing tools, Bookmarks, undo/redo, Save/Export, and zoom controls in their familiar roles. The Project widget lists board documents; it is not the hierarchy of objects inside a board.

One project can be active in a window. Do not spawn additional windows for New/Open Board or New/Open Project in v1. A second open request for an already-owned canonical project focuses the owning window, or explains that the project is in use if focusing is unavailable. Never offer a force-open writer while the owner is live; native storage handles stale-owner verification.

A project consists of a versioned JSON `.depthproject` manifest and independent `.depthplan` files in one folder. Import accepts current-format `.depthplan` and legacy `.depthplan.json` files and copies them into the project. Share or relocate the complete folder; the manifest alone does not contain the diagrams. No cloud accounts, collaboration, shared live objects, historical backups, or project archives are part of v1. Search across board content and inter-board links remain separate follow-ups.

## 2. Entry points and navigation

The existing application menu retains New Board, Open Board, Open Recent, Save, Save As, and Export. Add New Project, Open Project, and Recent Projects. In project mode, also expose Save All, Project Settings, and Close Project. New Board creates a member when a project is active; Open Board always means a standalone document. Import Board is the explicit project-copy action. Label native menu actions consistently with these meanings.

The standalone top-left card continues to show the document name and its save state. In project mode it shows the project name and active board/status, with a toggle for the floating board drawer. A project menu provides project actions. The drawer lists every member in project order; the tab strip lists only open sessions. Closing a tab does not remove membership. Selecting an already-open board activates its existing session.

| Launch without an open request                          | Existing blank canvas, with New/Open/Recent Project available from the menu. No automatic reopening of the last project.                                                                                  | Recovery candidates are offered without silently replacing the blank board.                                                                                                                                                                |

Create a new folder, manifest, and first board; open the Project widget in the same window.  | Validate the destination and resolve current work before writing. Do not switch until creation succeeds. Failed creation preserves the current workspace and reports any recoverable partial output. Never overwrite a preexisting folder. |
| Open Project / recent / native `.depthproject` open     | Validate the manifest and ownership, run current-workspace guards, then open the project in this window. Native cold/warm requests follow this same path.                                                 | Invalid manifest or live owner leaves current work untouched. Missing individual members do not reject a valid project. Queue multiple native requests; canceling one does not bypass guards on the next.                                  |

New Project with Copy current board first resolves active drafts. It copies the latest applied snapshot with a fresh document identity, including accepted unsaved edits. The original file is never modified by the copy. Successful copy satisfies the preservation requirement for that captured snapshot; failed copy or newer edits prevent disposal. Choosing Blank board uses the ordinary Save/Discard/Cancel guard for existing unsaved work. The new first board is named Overview (or the copied board's name), is set as home, and opens immediately. Autosave defaults on.

Restore valid local open tabs, active board, and camera state when a project is explicitly reopened. If no usable local workspace exists, open the configured healthy home board, otherwise the first healthy member in project order. If none is healthy, keep the project open with its empty/problem state. A deliberately saved workspace with no open tabs remains empty. With no active board, document editing, Save, Export, Bookmarks, and history controls are disabled; project create/import/open/settings actions remain available. Missing tabs are reported and skipped; corrupt local preferences fall back without modifying shared files.

Recent Projects is local to the user. Show name and location, with Locate and Remove from Recents for unavailable paths. Locate validates the selected manifest and identity; a different project is opened as a different entry, not silently rebound. Opening a copied folder does not inherit another location's tabs or writer ownership. When explicitly locating a moved project, matching identity and the unavailable old location allow local-state migration after user confirmation.

## 3. Ownership, identity, and dirty state

| Owner            | Data                                                                                                                              | Changes that affect persistence                                                                                                                                          |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Project manifest | Stable project identity, name/description, ordered board identities and relative paths, optional home board, autosave preference. | Membership/order/settings changes require guarded manifest writes. They do not dirty board content.                                                                      |
| Board document   | Independent document identity, objects, connections, content, styles, layouts, named bookmarks, supported extensions.             | Applied edits and authored bookmark changes dirty that board only. Existing document validation remains authoritative.                                                   |
| Local workspace  | Project identity plus canonical location, open tabs/order, active board, normal camera navigation, window/panel state.            | Store user-local; never dirty project or board files. A bookmark's deliberately authored camera snapshot still belongs in its board.                                     |
| Open session     | Unique session identity, revision, saved snapshot, undo/redo, selection, in-flight operations, supported drafts.                  | Kept per board while open. Save preserves history. Closing/reopening creates a fresh session and does not promise undo retention.                                        |
| Recovery store   | Applied document snapshots, project/location/board/session provenance, revision and timestamp.                                    | Independent of source saving; excludes draft text, explicit form drafts, history, ordinary camera, and selection. Recovery provenance never grants overwrite permission. |

Use a board's persistent document identity as its membership identity within a project; session identity is separate. Rename/reorder preserve identity. Import and Duplicate create fresh document identities and independent files; local object/bookmark references remain valid within that copied document and do not bind to the original. Never infer identity from a title. Display names may repeat; distinguish results with a relative filename/location and accessible secondary text. Source paths and stable identities are validated at native boundaries.

Project paths stay within the selected root after canonical/symlink resolution. Whole-folder copies retain internal identities but are separate locations; they cannot hijack the original's live sessions. A canonical board file already owned by another live session must not acquire a second writer through standalone opening. Technical schema bounds and locking algorithms belong to #12; their visible failure outcomes follow this specification.

## 4. Board operations and settings

All board operations are available from a named drawer control/context menu and keyboard navigation. Reorder also has Move Up/Move Down actions; drag is optional convenience. Search in the drawer matches board names, not board content. A separate menu action Open Board in Project focuses the same filter/list as a quick switcher; avoid introducing a conflicting global shortcut in v1.

| Operation           | v1 behavior                                                                                                                                                                                                                                                                                                                   |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| New Board           | Ask for a nonempty name; create an independent blank `.depthplan` file, append membership, open the board. Preview any generated filename suffix needed to avoid collisions.                                                                                                                                                  |
| Import Board        | Native multi-file picker; validate each selected payload before copying. Show per-file success/failure; healthy imports remain explicit successes. Each successful copy gets fresh identity and an unused project-relative filename. Original files stay intact. Do not list failed copies as members.                        |
| Rename              | Rename the board label and corresponding file through the native guarded operation; preserve identity, home reference, session, and history. Preview the target filename. File/draft/save activity is serialized before renaming. On failure retain the old valid mapping or show explicit recoverable-operation diagnostics. |
| Duplicate           | Resolve the source's active drafts, then copy its latest applied revision to a fresh document with valid internal references; append and open it. Suggest a Copy name and unused filename. Do not mark the source saved or overwrite it.                                                                                      |
| Reorder             | Change manifest order only; open-tab order stays user-local. Failure restores the displayed committed order and reports the error.                                                                                                                                                                                            |
| Remove from Project | State "The board file will remain in the project folder." Resolve the open board's drafts/edits first, then remove membership and its tab. Failure keeps membership. Clear the home setting if it points here. No file-delete action is included.                                                                             |
| Project Settings    | Name, description, optional home board, autosave on/off, location and Reveal in File Manager. Save changes and Cancel are explicit. Validate home membership. Changing display name never renames the project folder/manifest or restyles boards. Save failure keeps the form and unsaved values visible.                     |

Validate names and resulting paths against supported filesystem rules before mutation. Trim surrounding whitespace; reject empty names, control characters, path separators, unsafe/reserved filenames and unrepresentable destinations with field-level text. Compare destination collisions conservatively across case/Unicode normalization. Case-only renames of the same file are supported safely or rejected without changing the original. Never silently overwrite a different board or unrelated file. Duplicate labels can remain distinguishable through filenames; filename collisions use a reviewed suffix or a corrected name.

Manifest membership is authoritative. Unlisted files after an interrupted operation are not silently adopted or deleted: identify them as recoverable output and offer explicit retry/import or Reveal. A corrupt manifest cannot replace the current workspace. A valid manifest with missing/corrupt members shows those rows and keeps healthy members available. For a missing member, Retry rechecks its registered path; Restore file explains the expected location; Remove retains any remaining file. Replacing it with a different board uses explicit import rather than silently taking over its identity.

Removing the home board clears the home setting. Removing the last member is valid and shows the empty project. Settings offers None for home. On subsequent opening, use the restoration/home/first-healthy fallback from section 2.

## 5. Drafts and transition precedence

Unfinished inline text and explicit board forms remain in memory with their originating board during tab switches. Returning restores the draft and relevant focus. A tab/drawer navigation click is not an ordinary outside-click commit. Ordinary inline editing within the active canvas retains its existing acceptance behavior; explicit Apply/Cancel forms never commit merely because focus moved.

Before disposing/replacing a session (close, remove, reload, restore, project switch, quit), present Apply / Discard draft / Cancel. Apply validates and creates the ordinary undoable edit; invalid drafts keep the transition pending. Discard draft drops only that unapplied draft. Cancel aborts the transition. Then handle any applied unsaved work. A project-settings modal remains modal: finish Save changes/Cancel before switching boards or replacing the project; a canceled close leaves the form intact.

Drafts are not crash-recoverable in v1. Show "Draft not saved" while a draft exists, even when all applied edits have reached disk. Do not promise draft retention across closing, process crash, or machine restart. Autosave does not apply drafts. Save/Save All may persist applied revisions while leaving drafts visible and unprotected; report that distinction.

Resolve overlapping conditions in this order: finish/cancel an active pointer gesture; resolve any draft for a disposing transition; detect file/manifest conflict; await/recheck in-flight writes; persist or explicitly discard remaining applied changes; commit the workspace transition. Check the latest revision again before disposal. Cancel preserves all open sessions; intentionally applied/saved work remains applied/saved. Unexpected native shutdown offers recovery for acknowledged applied snapshots only.

## 6. State/transition table

States can coexist; use the precedence above. "Close" below includes tab close, removal, project/standalone replacement, and quit, restricted to the affected sessions. Project transitions aggregate all sessions. Reload/Restore always replaces a session and creates fresh history.

| ------------------------------ | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |

Close view only; membership is unchanged unless explicitly removing. | Validate target; replace with fresh session. Restore creates unsaved work.                                                           |
| Applied unsaved edits          | Keep edits and history; autosave may continue for the inactive board.                | Save captured revision; clear dirty only if current applied revision matches successful persistence. | Autosave on: attempt flush. Autosave off: Save / Discard changes / Cancel. Failed or canceled save keeps the session.   | Guard current changes first, validate replacement, then replace. ## 7. Save, conflict, close, and recovery behavior

Save and Cmd/Ctrl+S target the active board. Save All is a project-menu action for changed open boards; unopened boards are not loaded merely to save. Export uses its captured board and preserves the current export behavior; it is never an editable-document Save. Save As in project mode writes an independent standalone copy with fresh document identity, leaving project membership and the current board's save destination unchanged; name the action Save a copy in the project UI to avoid implying a move. Standalone Save As retains the existing destination-switching behavior.

Project autosave persists applied board edits after approximately one second idle and attempts at least one eligible save after five seconds of sustained applied edits, subject to I/O and failures. These are scheduling targets, not durability guarantees. Coalesce revisions and serialize writes per board; inactivity of a tab does not stop its eligible saves. Turning autosave off stops scheduling new source writes after the setting is persisted; an in-flight write can finish. Newer edits remain unsaved. Turning it on schedules eligible pending revisions, never conflicted writes. Recovery scheduling remains independent.

Membership/settings changes always persist through explicit guarded manifest operations, even when board autosave is off. A pending settings form does not become persistent merely because Save All was used. Manifest conflict pauses manifest mutations and any operation whose membership/path ownership is now uncertain; unaffected board saves may continue only where the native layer verifies the same safe target.

| Visible status            | Meaning and action                                                                                                                                     |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Saved                     | The latest applied revision is acknowledged on disk and no unprotected draft is hidden by this label.                                                  |
| Draft not saved           | An unapplied draft exists. Detail can say "Applied changes saved. Apply this draft to save it."                                                        |
| Unsaved changes           | Applied edits are pending; Save is available. With autosave off, this is normal until manually saved.                                                  |
| Saving…                   | A source write is in progress. A newer pending revision is not falsely marked saved by an older write.                                                 |
| Save failed               | Persistent error text and Retry / Save a copy. Reveal details without exposing credentials.                                                            |
| Changed outside DepthPlan | A source/manifest conflict paused affected writes; open the resolution dialog.                                                                         |
| Recovery unavailable      | Recovery checkpoint protection is degraded. Separate from whether the source save succeeded; do not claim the board itself is unsaved if it was saved. |

Use labeled row icons/text and a compact project summary (for example, "2 boards need attention" or "1 draft not saved"). The summary is never just a colored dot. For combined states, show the highest-actionable error and list draft/pending details in its accessible description. Do not announce "All saved" while settings, any board revision, or an unprotected draft is outstanding. Autosave is not backup/version history; show that explanation in settings help and recovery copy rather than a routine disruptive warning.

For an externally changed board: Keep editing retains local work with autosave paused; Reload from disk resolves current draft/unsaved work before replacement; Save a copy preserves local applied data in a new file and leaves the conflicted original untouched; Overwrite requires explicit confirmation tied to the observed external version. A newer external version invalidates that confirmation. A saved conflict copy does not silently change the project member; reload the original or explicitly discard its local changes once they are preserved.

For a changed manifest: pause project mutations, retain the locally requested change/form, and offer Reload project definition or explicitly confirmed Overwrite project definition. Reload reconciles by stable identity. Open dirty/draft boards removed or repathed externally must be resolved or safely copied before their sessions are disposed; do not send them to new paths by inference. Reconciliation failure leaves the workspace intact. Native transaction mechanics are #12's responsibility.

Close uses a single summary with each affected board, draft/save/conflict reason, and Review/Retry/Save a copy actions. Safe boards may finish saving, but no session is disposed until the requested aggregate transition can complete. Keep open is the default/cancel action. Discard choices explicitly name the board and the draft or applied changes being abandoned; no default-selected bulk discard. While autosave is off, the ordinary unsaved summary offers Save all and close, review/discard individually, or Keep open. If any save fails, remain in the summary. Never spin indefinitely behind a disabled close button.

Recovery on restart lists the board/project/location, timestamp, and whether a source is unavailable/changed. Restore creates a fresh dirty session, initially suspends automatic source replacement, and requires an explicit safe Save or Save a copy/conflict choice before normal autosave resumes. Skip leaves the candidate available; Discard recovery requires an explicit choice. Retire only checkpoints superseded by acknowledged persistence or explicitly discarded. Missing/corrupt recovery entries do not block healthy ones. Drafts and undo are not offered as recoverable.

## 8. Responsive and accessible interaction

Review reference sizes are 1440×1000 (wide), 1024×728 (current default window), and 900×640 (compact). These are design targets, not a new enforced app minimum. Below the compact target, retain reachable controls through wrapping/scrolling rather than clipping destructive dialogs.

At wide sizes the drawer is approximately 280px, floating below the top-left card; open tabs form a short strip beneath drawing tools. At compact widths (below 1100px), the drawer overlays the canvas and initially stays collapsed; show the active tab plus an Open boards overflow control instead of squeezing all names. Drawing tools can occupy a separate row beneath the identity/actions row. Keep Save/Export visible. Do not shrink text to fit. Long labels truncate visually but expose full names through accessible labels and focus/hover detail.

Dialogs are at most 560px wide, inset at least 16px from the window, and no taller than the available viewport minus 32px. Scroll the form/error list while keeping title and footer reachable. Aggregate close uses stacked board rows on compact windows. Startup remains the same canvas at every width. Existing Bookmarks and zoom remain in the lower corners, with overflow if required; overlays must not cover keyboard-focused controls without a way to dismiss them.

Use semantic buttons, labeled inputs, a named board list, and a tablist for open tabs. Each close button includes the board name. Tab enters/leaves the tablist; Left/Right and Home/End move focus within it; Enter/Space activates a focused tab (manual activation avoids surprise navigation). Drawer names can be searched; Up/Down move through results and Enter opens one. Escape clears an active filter first, then closes the drawer and restores its toggle's focus. Menu actions expose New/Import, Save All, and the board quick switcher without requiring a new shortcut.

Preserve existing New/Open/Save/Save As/Export shortcuts with mode-specific labels. Cmd/Ctrl+W closes the active project tab when one exists; in standalone mode it retains the existing guarded window-close behavior. Closing a project uses its explicit action. Do not bind a new Save All shortcut over existing Save As. Drawer reordering has Move Up/Down menu items so drag is never required.

Trap focus inside a modal; label its title and errors. Cancel/Escape closes a creation/settings dialog without applying pending values; destructive-resolution Escape means Keep open. If inline text owns Escape, retain the ordinary inline acceptance behavior and do not also trigger outer shortcuts. Focus returns to the invoker, the newly active tab after closing a tab, or the restored draft editor when returning to its board. After project creation/opening, announce project and active board and focus the canvas entry point; do not leave focus on a removed dialog control.

Save progress uses a polite status region with coalesced announcements; persistent failures include text and a focusable action. Avoid moving focus merely because an autosave completes. Error icons have accessible names and sufficient contrast; blue/red/amber alone never conveys the state. Respect reduced motion. The wireframe sheet is a visual design artifact; application accessibility and native keyboard tests remain required in #14/#19.
